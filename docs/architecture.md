# Architecture

Archivum is a Laravel 13 application with a React front end delivered through
Inertia. There is no separate API tier and no client-side router: the server
renders page props, Inertia hands them to a React component, and a form post
goes back to a normal Laravel controller.

```text
Browser
   │
   ▼
React + Inertia  ──  resources/js/pages/<name>.tsx
   │
   ▼
Laravel 13
   │
   ├── Middleware      workspace context, locale, Inertia shared props
   ├── Controllers     thin: authorize, resolve, delegate, render
   ├── Form Requests   validation and request-level authorization
   ├── Actions         the application's operations
   ├── Policies        who may do it
   ├── Eloquent        persistence
   ├── Scout           search
   └── Jobs            work that must not block a request
       │
       ├── MySQL
       └── File storage
```

## The core principle

> Logical organization and physical organization are separate concepts.

A document is categorised, tagged and searched independently of the cover,
folder, drawer or shelf its paper copy sits in. Everything in the domain model
follows from that: [documents](documents.md) and
[organization nodes](organization.md) are separate trees, joined by a
*location* record that carries its own history.

## Where each kind of logic lives

| Layer | Responsibility | Rule |
| --- | --- | --- |
| Controller | Authorize, resolve route bindings, delegate, render | No business logic, no multi-step writes |
| Form Request | Shape and validate input; `authorize()` for request-level checks | No business logic |
| Policy | Whether *this* user may act on *this* record | Membership is checked here, not in the controller body |
| Action | One meaningful operation, start to finish | Owns its own validation of domain rules, and its own invalidation |
| Job | An operation that must not block the request | Records its outcome on a `Task` row |
| Model | Persistence, relations, and small derived helpers | No orchestration |

`app/Actions/` is grouped by domain — `Documents/`, `Organization/`,
`Workspace/`, plus `Fortify/` for the auth callbacks the package expects.

An Action is the unit that gets tested. Most feature tests drive a controller,
but the rules that are hard to reach through HTTP — a guard the controller 404s
before, a branch only another caller can hit — are tested by calling the Action
directly, and say so in a comment.

## Things deliberately not here

**No repositories.** Eloquent is the persistence layer. A class whose only body
is `Document::query()` is indirection without abstraction.

**No service objects by default.** `app/Services/` holds exactly one thing —
`Ocr/`, which wraps external binaries and genuinely has more than one
implementation behind an interface. A service is justified by a real boundary
or a second implementation, not by symmetry.

**No tenancy package.** Workspace isolation is part of the domain model and is
enforced by policies and query scoping. See [workspace.md](workspace.md).

**No DTO or repository package, no Cashier, no Passport.** SaaS billing is out
of scope, and Sanctum covers the token needs the [API](api.md) has.

## Queues

Anything that would make a request wait on work proportional to the archive's
size runs on the queue:

| Job | Triggered by |
| --- | --- |
| `ExtractAttachmentText` | Every attachment upload — see [ocr.md](ocr.md) |
| `ExportWorkspaceDocuments` | The workspace Tasks page |
| `BulkMoveDocuments` | Migrating every document under one organization node to another |

Each one writes to a `Task` row, which is what the workspace's Tasks page
shows: status, who started it, what it produced, and a retry button when it
failed. That row is the user-facing half of the job — a failure that only
reached `failed_jobs` would be invisible.

Exports and bulk moves take a per-workspace lock through `Cache::lock()`, keyed
by `TaskType::lockKey()`, so a second one cannot start while the first runs.
Text extraction deliberately takes no lock: it is scoped to a single file, so
several run concurrently.

**Nothing queued runs unless a worker runs.** See [deployment.md](deployment.md).

## Front end

```text
resources/js/
├── actions/     generated by Wayfinder — controller actions as typed functions
├── routes/      generated by Wayfinder — named routes as typed functions
├── components/  shared UI, with ui/ holding the shadcn primitives
├── hooks/
├── layouts/     the app shell, the auth shell, the settings shell
├── lib/         helpers, including the i18n dictionaries
├── pages/       one file per Inertia page component
├── types/
└── wayfinder/
```

`actions/` and `routes/` are generated and git-ignored. They are rebuilt by the
Wayfinder Vite plugin on every build, which means **the build has to run inside
Sail** — it reads route parameter types from the live database, and a host build
that cannot reach MySQL types UUID keys as `number`. That trap is recorded in
`.ai/rules/general.md`.

Layout, spacing and colour conventions are in `.ai/rules/` — `pages.md`,
`layouts.md`, `components.md` and `css.md`. They exist because none of it is
caught by CI.

### Ordering a listing

Every listing — documents, tasks, activity, members, document types, tags,
workspaces, the review queue — can be reordered, and the choice travels in the
query string so a sorted page can be linked and returned to.

`App\Support\TableSort` does the server half. A controller declares the columns
its screen offers, resolves the request against that whitelist, and passes the
resolved order to the page as a `sort` prop. Nothing user-supplied reaches
`orderBy`, and a key outside the whitelist falls back to the listing's default
rather than raising. Every order ends in a tiebreaker: `paginate()` asks a fresh
question per page, so an order that leaves ties lets a row appear on two pages or
on none.

`resources/js/components/sortable-table.tsx` does the other half. A page declares
its columns once and passes them to both controls, so they cannot drift apart:
`SortableTableHead` for the clickable column heads, and `SortMenu` for a menu
carrying the same list. The menu is rendered at every width, not below a
breakpoint — a table scrolls sideways on a phone, so its heads are off-screen
exactly where they are hardest to reach, and the documents card layout has no
heads at all.

Routes are split by area — `documents.php`, `organization.php`,
`workspaces.php`, `attachments.php`, `invitations.php`, `settings.php` — rather
than living in one `web.php`.

## Authentication

Session authentication through Laravel Fortify, rendered by Inertia. Fortify
supplies login, password reset, email verification, two-factor authentication
and passkeys; the React screens live in `resources/js/pages/auth/`.

There is **no public registration route**. Accounts exist because the seeder
created the first administrator, or because an existing admin invited the
person by email.

Token authentication for the API uses Sanctum. The two flows are independent.
